# openENOC CSR-Based Test Suite

## Overview

This test suite validates the CSR access path used by the openENOC register-level verification environment.

The test exercises a PeakRDL-generated CSR RTL block through an AXI4-Lite interface and verifies register behavior using the corresponding PeakRDL-generated Python register model. The Python model is connected to the simulated RTL through read and write callbacks, allowing software-style register tests to drive actual bus transactions in simulation.

The same register test functions are also reused by a hardware-oriented test entry point. This keeps the test logic independent of whether register accesses are performed against simulated RTL or through a hardware access layer.

## Tooling

This project uses the following tooling:

* **[oss-cad-suite-build](https://github.com/yosyshq/oss-cad-suite-build)** - Open source CAD tools suite, including Verilator
* **OS:** Ubuntu 24.04

## Test Structure

The verification environment consists of:

* `Makefile` - cocotb simulation entry point using Verilator
* `testbench.py` - cocotb testbench that creates the clock, reset, AXI4-Lite master, CSR model, and test execution wrapper
* `rtl_simulator.py` - bridge between the synchronous PeakRDL callback API and asynchronous cocotb AXI4-Lite transactions
* `tests.py` - reusable software-style register tests
* `hardware_test.py` - standalone hardware-oriented test entry point that reuses the same register tests
* `hardware_interface.py` - placeholder hardware interface intended to be replaced by a real access mechanism such as JTAG
* `__init__.py` - package metadata and exported symbols

The RTL and Python register model are generated by PeakRDL and are expected to be available under the common build directory.

## Generated Inputs

The Makefile expects the PeakRDL-generated artefacts to be located in:

```Makefile
ENDPOINT          = openenoc_full_endpoint
BUILDDIR          = $(abspath $(CURDIR)/../../../build/hal)
ENDPOINT_BUILDDIR = $(BUILDDIR)/$(ENDPOINT)
PEAKRDLRTL        = $(ENDPOINT_BUILDDIR)/rtl
PEAKRDLPYTHON     = $(ENDPOINT_BUILDDIR)/python
```

The RTL simulation uses the generated CSR package and top-level CSR module:

```Makefile
VERILOG_SOURCES += $(PEAKRDLRTL)/$(TOPLEVEL)_pkg.sv
VERILOG_SOURCES += $(PEAKRDLRTL)/$(TOPLEVEL).sv
```

The generated Python register model is added to `PYTHONPATH` so that the cocotb testbench and hardware test can import the same register abstraction:

```Makefile
export PYTHONPATH := $(CURDIR):$(PEAKRDLPYTHON):$(PYTHONPATH)
```

## Testbench Architecture

The cocotb testbench targets the generated endpoint-prefixed CSR RTL module:

```Makefile
TOPLEVEL = $(ENDPOINT)_csr
COCOTB_TEST_MODULES = testbench
```

During simulation, the testbench starts a 10 ns clock, applies reset, creates an AXI4-Lite master from the `s_axil` bus prefix, and connects the generated Python CSR model to the simulated RTL through callback functions.

```python
axi_bus = AxiLiteBus.from_prefix(dut, "s_axil")
axi_master = AxiLiteMaster(axi_bus, dut.clk, dut.rst)

hw = RTLSimulator(axi_master)

csr = csr_cls(
    callbacks=NormalCallbackSet(
        read_callback=hw.read,
        write_callback=hw.write
    )
)
```

The `RTLSimulator` class adapts the blocking register access model used by the PeakRDL Python model to the asynchronous cocotb simulation environment. Register reads and writes are placed into a request queue, processed by a cocotb worker coroutine, and completed through AXI4-Lite transactions.

This allows the register tests to be written as normal Python functions while still driving the RTL through the actual bus interface.

## Test Configuration

The main simulation configuration is defined in the Makefile:

```Makefile
TOPLEVEL_LANG = verilog
SIM = verilator
TOPLEVEL = $(ENDPOINT)_csr
COCOTB_TEST_MODULES = testbench
```

Simulation output is placed under:

```Makefile
SIM_OUTPUT = $(abspath $(CURDIR)/../../../build/dv/hal/$(ENDPOINT))
SIM_BUILD = $(SIM_OUTPUT)/sim_build
```

Verilator is configured for SystemVerilog input and waveform tracing:

```Makefile
EXTRA_ARGS += --sv
EXTRA_ARGS += --trace
EXTRA_ARGS += --trace-fst
EXTRA_ARGS += --trace-structs
EXTRA_ARGS += -Wall $(CURDIR)/../../common/config.vlt
```

## Running Tests

This test is executed directly through cocotb and the cocotb Makefile flow. It does not use pytest or cocotb-test.

To run the RTL simulation:

```bash
make
```

This builds the generated CSR RTL with Verilator, runs the cocotb tests from `testbench.py`, and executes the register tests defined in `tests.py`.

To remove generated simulation artefacts:

```bash
make clean
```

## Waveform Debugging

Waveform tracing is enabled through the Verilator arguments in the Makefile. After running the simulation, the generated FST waveform can be opened with:

```bash
make wave
```

This launches:

```bash
gtkwave dump.fst
```

The waveform flow is intended for debugging AXI4-Lite transactions, reset behavior, register read/write timing, and callback-driven register accesses.

## Hardware-Oriented Test Flow

The same register tests can also be executed through the hardware-oriented entry point:

```bash
make hwtest
```

This runs:

```bash
python -m hardware_test
```

The hardware test creates a `HardwareInterface` instance and connects it to the same PeakRDL-generated Python register model through the same `NormalCallbackSet` mechanism used in simulation.

At this stage, `HardwareInterface` is a placeholder implementation backed by the generated simulator class. It prints register accesses and is intended to be replaced by a real hardware access layer, such as a JTAG, debug bridge, or other board-specific transport.

## Test Flow

Each cocotb test performs the following sequence:

1. Start the simulation clock.
2. Assert reset.
3. Release reset after the configured reset interval.
4. Create an AXI4-Lite master connected to the generated CSR RTL.
5. Start the `RTLSimulator` worker coroutine.
6. Create the PeakRDL-generated Python CSR model.
7. Connect the CSR model to the simulator through read and write callbacks.
8. Run the selected software-style register test in a separate Python thread.
9. Convert register model reads and writes into AXI4-Lite bus transactions.
10. Report any assertion failure from the register test back to cocotb.

The use of a separate Python thread allows blocking software-style register tests to coexist with the asynchronous cocotb event loop.

## Register Tests

The current test suite includes two register tests.

### `test1`

Writes a value to `test_reg.test_field` and verifies that the same value can be read back:

```python
csr.test_reg.test_field.write(123)
assert csr.test_reg.test_field.read() == 123
```

### `test2`

Verifies read/write behavior for writable fields in `regB` and checks the default value of read-only or unwritten fields:

```python
csr.regB.f0.write(45)
assert csr.regB.f0.read() == 45

csr.regB.f1.write(67)
assert csr.regB.f1.read() == 67

assert csr.regB.f2.read() == 0
assert csr.regB.f3.read() == 0
```

## Test Coverage

The test suite currently covers the following scenarios:

### CSR Model Integration

Verifies that the PeakRDL-generated Python register model can access the generated CSR RTL through callback functions.

Coverage includes:

* CSR model construction
* Read callback connection
* Write callback connection
* Field-level register access
* Software-style test reuse

### AXI4-Lite CSR Access

Verifies that register model accesses are translated into AXI4-Lite transactions in simulation.

Coverage includes:

* AXI4-Lite read transactions
* AXI4-Lite write transactions
* Little-endian data conversion
* Access-width-based transfer sizing
* Blocking register API synchronization with cocotb transactions

### Register Read/Write Behavior

Verifies basic register storage and readback behavior.

Coverage includes:

* Writable field write/read access
* Multiple fields within the same register block
* Default zero-value checks for selected fields
* Assertion-based failure reporting

### Simulation and Hardware Test Reuse

Verifies that the same register test functions can be reused across different access backends.

Coverage includes:

* cocotb RTL simulation backend
* hardware-oriented callback backend
* shared `tests.py` register test implementation
* backend-independent register access logic

## Notes

This test is intended to validate the CSR verification infrastructure rather than exhaustively verify a production CSR map.

The current register tests are simple smoke tests. They confirm that the generated Python model, callback layer, AXI4-Lite simulation bridge, and generated RTL can operate together correctly.

The `hardware_interface.py` implementation is currently a dummy placeholder. A board-specific implementation can replace it while preserving the same `read()` and `write()` callback interface.

The test flow is cocotb-only. It does not use pytest, cocotb-test, or parameterized pytest regressions.

Additional register tests can be added by extending `tests.py` and exposing them through new `@cocotb.test()` wrappers in `testbench.py`, or by calling them from `hardware_test.py` for hardware-oriented validation.
